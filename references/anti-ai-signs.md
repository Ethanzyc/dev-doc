# 反方案 AI 味清单

> 终审（Phase 5）和核心设计评审（Phase 3）时逐条对照。
> 任何一条命中就标出并要求修正。
> **目录**：通用部分（1 空话架构 / 2 无 trade-off / 3 放之四海皆准 / 4 无数据量 / 5 无风险回滚 / 6 过度设计）· 后端特有（7 DDL 无估算 / 8 状态机不完整 / 9 接口契约模糊 / 10 测试方案空洞）· 评审输出格式 · SubAgent 调用模板

## 使用方式

评审时**必须以"问题清单"形式**给出，不是"通过/不通过"。每条命中要指出：在文档哪个章节、具体哪句话、为什么是问题、应该怎么改。

## 通用部分（所有方案适用）

### 1. 空话架构

**反模式**：只说"采用微服务架构""使用 Redis 缓存""引入消息队列"，没有任何具体细节。读者看完依然不知道这个选型怎么落地。

**正确做法**：每个技术选型写清楚——
- 为什么用（要解决的明确问题）
- 容量估算（预估的 QPS / 数据量 / 连接数）
- 关键配置（淘汰策略 / 分片方式 / 超时时间）
- 失效场景（缓存击穿 / 雪崩 / 一致性问题怎么处理）

**自检问题**：如果删掉这句话，方案会缺什么？如果缺的是"决策依据"而不是"事实陈述"，就是空话。

### 2. 无 trade-off

**反模式**：只写选了什么，不写为什么不选别的。看起来每个决策都"理所当然"，但读者无法判断这个选择对不对，也无法在出问题时快速定位。

**正确做法**：每个关键决策带——
- 考虑过哪些备选（至少 1 个）
- 为什么不选它们（具体的、和本项目相关的理由）
- 当前选择的代价是什么（明确点出）

**自检问题**：这个决策有没有"显而易见的备选"？如果有却没提，就是无 trade-off。

### 3. 放之四海皆准

**反模式**：方案套在任何项目都对。比如"采用分层架构，分为 controller/service/dao 三层"——这句话放在任何 Java 项目都成立，没有信息量。

**正确做法**：必须结合本项目的——
- 数据量（具体数字或量级）
- 现状（现有代码/架构的约束）
- 业务约束（合规/性能/团队能力的特殊要求）

**自检问题**：把"本项目"换成"另一个项目"，方案还成立吗？如果成立，就是太泛了。

### 4. 无数据量

**反模式**：只看表总行数设计（"这张表预计 1000 万行"），没有估算单次查询命中的数据量。

**正确做法**：结合查询条件估算**单次查询命中量**——
- 查询字段 + 数据分布 → 单次查询返回多少行
- 量级影响：分页策略（深分页？）/ 批量大小（一次处理多少）/ 是否需要异步
- 拿不准找用户确认具体数据量，不要自己假设

**自检问题**：方案里的分页/批量/同步异步选择，有没有数据量依据？没有就是拍脑袋。

### 5. 无风险/回滚

**反模式**：只写怎么做，不写出事怎么办。风险评估章节是"无重大风险"或抄模板，回滚方案是"代码回滚"一句话。

**正确做法**：风险评估 + 回滚方案是**必备章节**——
- 风险评估：技术/业务/数据/性能四类，每类列具体风险 + 缓解措施
- 回滚方案：DDL 变更怎么回滚（数据怎么处理）/ 灰度发布怎么回退 / 是否有不可逆操作

**自检问题**：如果这个方案上线后 P0 故障，最可能的根因是什么？这个根因在风险评估里吗？回滚可行吗？

### 6. 过度设计

**反模式**：小改动套大架构。给一个字段加默认值，写了 3 页架构设计、引入了新中间件、规划了灰度发布。

**正确做法**：重量分级——
- 轻方案不写架构章节（直接写改动点和工时）
- 章节深浅和方案重量匹配（见 plan.md 的章节规划表）
- 简单的改动就简单写

**自检问题**：这个方案的复杂度和改动的实际复杂度匹配吗？是不是为了凑章节而强行展开？

## 后端服务特有

### 7. DDL 无估算

**反模式**：不看数据量和查询模式就加索引。每张表都堆 5 个索引，每个字段都可能加索引"以防万一"。

**正确做法**：索引设计结合——
- 表数据量（行数 + 增长速度）
- 实际查询模式（哪些是高频查询、哪些是低频）
- 写入成本（索引越多写入越慢）
- 明确说明每个索引服务的查询

**自检问题**：每个索引都说得出"它服务哪个查询"吗？说不出就是冗余索引。

### 8. 状态机不完整

**反模式**：只画状态流转图，不写每个流转的触发条件、副作用、守卫条件。读者看到"待支付 → 已支付"不知道是什么触发的、有没有副作用。

**正确做法**：每个状态流转写清楚——
- 触发条件（什么事件/动作触发流转）
- 副作用（流转时发生了什么：发消息、改其他表、调外部接口）
- 守卫条件（什么情况下不能流转，比如已退款的单不能再次支付）

**自检问题**：照着状态机，能不能复现每个流转的代码逻辑？不能就是不完整。

### 9. 接口契约模糊

**反模式**：接口文档写"返回成功/失败"或者"返回错误信息"。调用方不知道成功长什么样、失败有哪些情况。

**正确做法**：接口契约精确——
- 完整的错误码列表（每个码对应什么场景）
- 幂等性（接口是否幂等，幂等键怎么设计，重复调用会怎样）
- 版本策略（接口是否版本化，旧版本怎么处理）
- 请求/响应的精确 schema（字段、类型、是否必填、取值范围）

**自检问题**：另一个团队的工程师照着这份接口文档，能不能直接写调用代码？不能就是不够精确。

### 10. 测试方案空洞

**反模式**：测试方案写"编写单元测试保证质量"或"覆盖核心场景"。读完不知道具体测什么。

**正确做法**：测试方案具体——
- 具体的测试类（命名、测哪个类的哪个方法）
- 覆盖场景（正常流程 / 边界条件 / 异常场景，逐一列出）
- 数据准备方式（构造什么数据、怎么构造）
- 集成测试的场景和数据准备方式

**自检问题**：照着这份测试方案，能不能直接写测试代码？不能就是太空洞。

## 评审输出格式

SubAgent 评审时按这个格式输出（问题清单，不是通过/不通过）：

```
## 评审：可行性 / 风险 / 成本

### 命中的反 AI 味条目
- [条目 N] 在 <章节>，<具体问题>，应改为 <建议>

### 其他发现的问题
- <问题>，影响 <什么>，建议 <怎么改>

### 需要用户确认的点
- <问题>（skill 无法自行判断，需用户拍板）
```

## 三视角评审 SubAgent 调用模板（Phase 3 / Phase 5）

Phase 3 / Phase 5 要求开 SubAgent 做独立评审。开之前必须避开两个坑：

1. **SubAgent 没有本 skill 的上下文**——它的工作目录是用户项目，prompt 里写"加载 references/anti-ai-signs.md"它找不到文件。正确做法：**把本文件"通用部分 + 后端服务特有"的 10 条清单全文直接粘进 prompt**（只有 10 条，注入成本远低于评审退化的风险）
2. 不显式要求"问题清单"输出，评审会退化成"通过/不通过"

### 通用 prompt 骨架

开 SubAgent 时，把下面这段连同**清单全文**、方案内容一起喂给每个视角的评审 SubAgent：

```
你是技术方案评审员，只从「<视角>」这一个视角评审下面的方案。

规则:
1. 对照 prompt 末尾贴出的「反方案 AI 味清单」逐条检查
2. 输出必须是「问题清单」，不是"通过/不通过"。每条命中指出：在哪个章节、具体哪句、为什么是问题、应怎么改
3. 没问题的点不写，只写有问题 / 有风险的点
4. 区分「必须改」（会导致方案跑偏/上线事故）和「建议改」（优化项）
5. 评不出来的（缺信息、需用户拍板）单列「需用户确认」

视角职责:
<视角说明>

待评审内容:
<粘贴方案文档全文，或本次评审的核心章节>

反方案 AI 味清单:
<粘贴本文件"通用部分 + 后端服务特有"的 10 条清单全文>
```

### Phase 3 三视角（可行性 / 风险 / 成本）

| 视角 | 视角说明（填入 prompt 的 `<视角说明>`） |
|---|---|
| 可行性 | 技术上能不能做：选型依赖是否具备、团队技术栈是否支持、有没有未验证的假设 |
| 风险 | 会出什么事：数据一致性 / 并发 / 回滚不了的场景 |
| 成本 | 值不值得：工时是否合理、是否过度设计、维护成本 |

### Phase 5 三视角（逻辑自洽 / 风险完整 / 可实现）

| 视角 | 视角说明 |
|---|---|
| 逻辑自洽 | 章节间是否矛盾：关键决策是否在所有章节一致、状态机/接口/DDL 是否对得上 |
| 风险完整 | 反 AI 味 10 条逐条核对、回滚/灰度/数据迁移是否覆盖 |
| 可实现 | 照着方案能否直接编码：改动清单是否全、接口契约是否精确到能写调用代码 |

> 开几个 SubAgent、按重量怎么裁剪（中/重开 3 个、轻方案可不开）、哪些核对项必须主 agent 做、评审结果不落盘——这些执行规则以 SKILL.md Phase 3.3 / 5.1 / 5.2 为准，此处不复述，避免两处维护漂移。
