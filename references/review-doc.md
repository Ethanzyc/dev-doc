# 评审版技术方案生成规则

> **用途**：主方案通过 Phase 5 交付确认后，按本规则从主方案生成面向技术评审的精简版。首次生成与变更后的重新生成都走这份规则。
> **定位**：主方案给编码 AI 看契约，评审版给人讲决策。评审版是**单向衍生品**——只从主方案生成、永不手动编辑，主方案是唯一事实源。

## 产物与命名

- 路径：`dev-doc/tasks/<feature>/<feature>技术方案-评审版.md`
- 文件头（固定写法，放在标题下方）：

```markdown
> 本文件为《<feature>技术方案.md》的评审版衍生品，面向技术评审（产品 / 测试 / 前端 / 后端协作者）。
> 内容以主方案为准，请勿直接编辑本文件；主方案变更后本文件自动重生成。
```

## 前置条件

- 主方案已通过交付确认（plan.md 状态为「已完成」）。主方案不完整时**不生成**，提示用户先补全主方案（fail fast，不拿半成品转换）。

## 章节结构（按配方分形）

**结构选择**：单一需求（generic-medium / greenfield 配方）用下方 1-9 节横切结构；**multi-task 配方（多个小需求打包）改用纵切的分形结构**（见下方「multi-task 分形结构」小节）——主方案的组织轴是什么，评审版就继承什么。

### 1. 需求
- **来源**：主方案「需求背景」+「需求说明」两节，合并压缩
- **写**：一段话说清做什么、为什么（5 行以内）——评审要的是"为什么开会"
- **不写**：业务场景罗列、PRD 复述、范围细节

### 2. 整体设计思路
- **来源**：主方案「整体设计思路」+「状态机」两节
- **写**：架构图（直接复用主方案「整体设计思路」的 mermaid）+ 设计主线 2-3 段；**状态机融入本节**：复用主方案「状态机」的 stateDiagram，每个流转一行触发条件
- **不写**：逐字段论证、模块职责长文、流转的副作用/守卫条件细节（主方案里有，评审不展开）

### 3. 数据模型
- **来源**：主方案「数据模型」节（+ 涉及迁移时其「数据库变更」节的 DML/迁移语句）
- **写**：DDL 原样保留（评审要拍板表结构），每个表一句话说明角色；**涉及存量数据迁移时附 DML/迁移语句**
- **不写**：索引逐个论证（索引定义留在 DDL 里即可）

### 4. 接口改动
- **来源**：主方案「接口契约」节 + 其「改动点/改动清单」的接口变更行
- **写**：
  - **新增接口：完整 schema**（路径/方法/请求响应字段/错误码）——前端第一次见
  - **变更接口：只给 diff**——「变更前 → 变更后」对照表，老接口前端熟
  - 每个接口一行影响方（谁调用/谁对接）
- **不写**：幂等性等实现细节（除非该点需要评审拍板）
- diff 对照表写法：

| 字段 | 变更前 | 变更后 |
|---|---|---|
| status | int（0/1/2） | string（PENDING/USED/EXPIRED） |
| expireTime | （无） | 新增，datetime，ISO8601 |

### 5. 关键流程
- **来源**：主方案「关键流程」节
- **写**：sequenceDiagram 原样复用 + 编号步骤文字（比主方案可再压缩）
- **不写**：算法伪代码级细节

### 6. 测试影响
- **来源**：主方案「改动点/改动清单」节 + plan.md「影响范围」的上下游依赖
- **写**：① 本次变更要测什么（2-4 条核心场景）② **受影响的现有功能清单（回归范围）**——由「改了什么 × 谁在用」推导，如"改了 VoucherService 状态流转 → 现有券列表页状态展示、ExpireVoucherJob 需回归"
- **不写**：测试类名、数据准备方式（主方案「测试方案」节的事）
- **这是唯一允许增量推理（非摘录）的一节**：推导不出上下游时如实写"暂无已知影响面，欢迎评审补充"，禁止编造

### 7. 风险评估
- **来源**：主方案「风险评估」节
- **写**：只留「评审要拍板」的风险（数据迁移、兼容性、跨团队依赖），每条一行缓解措施
- **不写**：四类风险凑满、常规性能风险的模板化内容

### 8. 上线顺序（仅特殊情况写）
- **来源**：主方案「上线方案」节
- **写**：仅当存在**特殊情况**才设本节——跨服务/跨引擎 provider 需先上、灰度开关/分批放开、模块间有上线依赖、有特殊回滚顺序。写清顺序（①②③）与各部分回滚独立性
- **不写**：普通"代码一起上线、无依赖、无灰度"时**不设本节**（连标题都不留，不是写"无特殊要求"）

### 9. 工时评估
- **来源**：主方案「工时评估」节
- **写**：表格原样照搬——工时是产品/管理直接消费的数字，不压缩

## multi-task 分形结构（需求打包场景）

多个小需求合在一个上线窗口时，横切结构会把每个子任务的故事打散（讲一个需求要在设计/流程/风险多节间跳）。改为**按子任务纵切**，每个子任务自成闭环讲完再讲下一个：

1. **需求**（同第 1 节定义）
2. **子任务总览**：表（子任务 / 影响范围 / 优先级 / 依赖，**不含工时列**——工时统一在末节）+ 一句主线（如"全部代码变更、无 DDL、可独立回滚"）
3. **逐个子任务**（每个子任务重复此块）：
   - **改动是什么**：改动点压缩为几行（改造/新增/接口变更）
   - **变更接口**：有才写（新增完整契约 / 变更 diff，写法同「接口改动」节定义）
   - **核心逻辑**：编号步骤或一段话；**流程图按需**——并发/事务/算法类子任务配图（复用主方案该子任务的图），简单校验类不配图
4. **测试影响**（同节定义——回归范围跨子任务，整体放）
5. **风险评估**（同节定义——含子任务间影响与回滚耦合，整体放）
6. **上线顺序**（同节定义，仅特殊情况写）
7. **工时评估**（同节定义，照搬）

## 生成纪律（铁律）

1. **图直接复用**：架构图/时序图/状态图从主方案原样复制，不重画不简化（主方案已过 mermaid-checklist 自检）
2. **有则写无则跳过**：主方案没有状态机/存量迁移/接口变更，对应内容不硬凑空节
3. **只裁不造**：除「测试影响」节的回归范围（明确允许推导）外，全部内容来自主方案摘录/压缩，禁止新增技术决策
4. **配方适配**：multi-task 走上方分形结构；greenfield 以「整体设计思路」节为核心，无接口改动则跳过「接口改动」节
5. **禁止手改**：生成后用户要调措辞 → 改主方案再重生成评审版，不直接编辑评审版文件；重新生成一律整篇进行，禁止只改部分章节的局部同步

## 生成后自检

| 检查项 | 标准 |
|---|---|
| 文件头标注 | 「以主方案为准」「请勿直接编辑」在 |
| 结构选对 | 单一需求用 1-9 节横切，multi-task 用分形纵切；有来源的都齐，无来源的没硬凑 |
| 接口写法 | 新增 = 完整 schema，变更 = diff 对照 |
| 图一致 | 与主方案一致，无重画走样 |
| 回归清单 | 「测试影响」节有受影响现有功能，或如实标「暂无已知」 |
| 上线顺序 | 仅特殊情况出现；普通上线不设该节 |
| 总览无工时 | multi-task 总览表不含工时列（工时只在末节） |
