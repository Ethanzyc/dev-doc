## 必备决策点

写后端服务方案时，以下决策点**必须想到**。不是每个都要深写，但要在方案里说明"为什么这个决策点对本需求不适用/不深究"。

### 1. 数据量估算

**什么时候要想**：涉及任何表读写、分页、批量、缓存的设计时。

**核心原则**：不是看表总行数，是**结合查询条件估算单次查询命中量**。

**要回答的问题**：
- 相关表的数据量（行数 + 增长速度）
- 单次查询命中多少行（结合查询字段的数据分布）
- 量级影响什么：分页策略（深分页？游标？）/ 批量大小（一次处理多少）/ 同步还是异步

**拿不准时**：找用户确认具体数据量，**不要自己假设**。假设的数据量是方案跑偏的常见根源。

**呼应**：`anti-ai-signs.md` 第 4 条（无数据量）。

### 2. 并发与一致性

**什么时候要想**：涉及库存/余额/计数/名额等"会争抢的资源"操作时。

**要回答的问题**：
- 是否需要锁？不需要的话靠什么保证一致（CAS？乐观重试？）
- 需要锁的话：乐观锁（version 字段）还是悲观锁（select for update）还是分布式锁（Redis/Zookeeper）？
- 锁的粒度：行锁？表锁？分布式锁的 key 粒度？
- 防超卖/防重复提交/防并发修改，分别怎么处理？

### 3. 事务边界

**什么时候要想**：涉及跨表/跨服务/外部调用的操作时。

**要回答的问题**：
- 事务边界在哪？（单库事务 / 跨库怎么保证 / 跨服务怎么保证）
- 是否需要分布式事务？需要的话用什么方案（TCC / Saga / 本地消息表 / 最终一致）
- 外部调用放在事务内还是事务外？（放内会拉长事务、放外会有一致性问题）

### 4. 幂等性

**什么时候要想**：对外提供接口、涉及支付/扣减/创建等"不可重复"操作时。

**要回答的问题**：
- 接口是否需要幂等？（什么场景下会重复调用：用户重试 / 网络重试 / 消息重复消费）
- 幂等键怎么设计？（业务唯一键 / token / 时间窗口）
- 重复调用返回什么？（返回上次的结果 / 返回"已处理"）

### 5. 状态设计

**什么时候要想**：涉及有生命周期的业务对象（订单/券/任务/流程）时。

**要回答的问题**：
- 状态用枚举（不用 magic number），code 类型与数据库列类型一致
- 每个状态流转：触发条件 + 副作用 + 守卫条件
- 是否需要状态机框架？还是简单的 if/switch 够用？

**呼应**：`anti-ai-signs.md` 第 8 条（状态机不完整）。

## 必备章节规范

在通用骨架基础上，后端服务方案**必须**包含以下章节（具体内容深度按重量分级决定）：

### 数据模型（DDL + 索引 + 约束）

- DDL 必须遵循团队规范（命名/主键/字段类型/索引命名）—— **具体规范走规范源**（Phase 1.3.0 探测；可能是 `.claude/rules/sql.md` 或 `conventions/sql.md`），不要硬编码
- 每个索引说清楚"服务哪个查询"
- 索引设计结合数据量（呼应 `anti-ai-signs.md` 第 7 条）
- DDL 用代码块包裹

### 接口契约（路径/方法/请求响应/错误码/幂等）

- 路径版本化（`/api/v1/...`）
- 完整的错误码列表
- 幂等性说明（呼应 `anti-ai-signs.md` 第 9 条）
- 请求/响应的精确 schema（字段/类型/是否必填/取值范围）
- API 设计用代码块包裹

### 状态机（枚举 + 流转图 + 流转条件）

- 状态枚举值
- mermaid `stateDiagram-v2` 画流转图
- **文字说明**每个流转的触发条件 + 副作用 + 守卫条件

### 改动清单（删/改/新增）

用表格：

| 类型 | 内容 |
|---|---|
| 删除 | 需要删除的文件/类 |
| 改造 | 需要改造的文件/类及改造点 |
| 新增 | 新增的文件/类 |
| 接口变更 | API 签名变更说明 |

### 数据库变更（DDL + 迁移 + 回滚）

- 表结构变更（含 DDL）
- 索引变更
- 数据迁移方案（存量数据怎么处理）
- **回滚方案**（DDL 怎么回退、数据怎么恢复）

## 反 AI 味要点（本领域特有）

以下要点和 `anti-ai-signs.md` 第 7-10 条呼应，写方案时主动避免：

- ❌ **只写"使用 Redis 缓存"不写**：命中率预估 / 淘汰策略 / key 过期 / 缓存击穿处理 / 数据一致性怎么保证
- ❌ **DDL 没有估算单表数据量就加索引**
- ❌ **状态机只画图不写**流转的触发条件、副作用、守卫条件
- ❌ **接口只写"返回成功/失败"不写**错误码、幂等性、版本策略
- ❌ **测试方案只写"编写单元测试"不写**具体的测试类、覆盖场景、数据准备方式

## 工时评估参考

按接口粒度评估。以下工时是参考基线，具体结合方案复杂度调整：

### 评估表

| 类型 | 工时 | 适用场景 |
|---|---|---|
| 基础设施 | 2-3h | 模型、实体类、枚举、DTO 一次性搭建 |
| 简单接口 | 1-1.5h | 单表 CRUD、字段修改、状态切换 |
| 中等接口 | 2h | 多步骤校验、批量操作、并发控制（锁）、树结构计算 |
| 复杂接口 | 3-4h | 跨模块改动、复杂业务编排、多表事务 |
| 改动现有方法 | 1h | 在现有方法中追加逻辑（如追加 CompletableFuture）|
| 测试 | 实现工时 ~40% | 单元测试 + 集成测试 |
| 联调 | 3-4h | 和前端联调自测 |

### 输出格式

工时章节用表格：

| 功能 | 明细 | 工时(h) |
|---|---|---|
| 业务功能点 | 接口路径 / Job / 方法名 | x |
| | ... | ... |
| 测试 | 单元测试 + 集成测试 | x |
| 联调 | 和前端联调自测 | x |
| | **合计** | **xx** |

### 使用约束

- 按接口粒度拆分，不要笼统写"业务开发 20h"
- 复杂度判断要有依据（哪个接口为什么是"复杂"而不是"中等"）
- 合计工时要能对得上方案里的改动点清单
