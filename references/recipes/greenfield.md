# 配方：新项目（greenfield）

> **适用场景**：新项目，从零开始。
> 重量判定通常为"重"。
> 后端领域决策点引用 `_backend-domain.md`。

---

## 核心差异（和 generic-medium 的区别）

1. **无"改动点"章节** —— 全是新建，没有删/改现有代码
2. **无"数据库变更（迁移/回滚）"章节** —— 新建表没有存量数据迁移问题
3. **重点在架构选型和里程碑规划** —— 新项目最大的不确定性是技术选型和交付节奏

---

## 文档结构

### 1. 项目背景与目标

**写什么**：
- 业务背景（这个项目服务于什么业务、解决什么问题）
- 项目定位（在产品矩阵中的位置、和现有项目的关系）
- 成功标准（怎么衡量这个项目做成了，能量化的指标优先）

**不该写什么**：不要写空泛的"赋能业务、提升体验"。

### 2. 架构设计

这是新项目方案**最核心**的章节。

#### 2.1 整体架构

- mermaid `flowchart` 画整体架构（见 `mermaid-checklist.md`）
- 说明各层的职责边界
- 节点不超过 15 个，复杂的拆子图

#### 2.2 技术选型

**每个关键选型必须写**（呼应 `anti-ai-signs.md` 第 2 条无 trade-off）：

```markdown
#### 选型：<选型主题，如"消息中间件">

**选项对比**：
| 选项 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| RocketMQ | ... | ... | ... |
| Kafka | ... | ... | ... |
| RabbitMQ | ... | ... | ... |

**选择**：RocketMQ

**理由**：结合本项目的 <具体约束>，因为 <具体理由>。
**代价**：<明确点出这个选择的代价>
```

新项目必做的选型（按需增减）：
- 语言/框架
- 数据库（单库/分库/读写分离）
- 缓存
- 消息中间件
- 部署方式（容器/物理机/Serverless）

#### 2.3 模块职责划分

- 每个模块的职责（一句话能说清）
- 模块间的调用关系（mermaid）
- 模块边界的划分依据

#### 2.4 数据流

- 核心业务的数据流向（mermaid `sequenceDiagram` 或 `flowchart`）
- 同步/异步的边界在哪

### 3. 工程结构

- 包结构 / 分层规范 / 命名规范
- **引用动态发现的 `conventions/project-structure.md`**（这是项目级规范，强相关）
- 如果是新项目还没规范，在这里**定义**规范（用户确认后写入 conventions）

### 4. 数据模型

- 核心表设计（不是所有表，是核心的）
- **遵循 `_backend-domain.md` 的 DDL 规范**
- 索引设计结合预估数据量（呼应 `anti-ai-signs.md` 第 4、7 条）

### 5. 接口契约

- 核心接口（不是所有接口，是核心的）
- **遵循 `_backend-domain.md` 的接口规范**
- 对外暴露的 API 边界

### 6. 部署架构

- 环境规划（开发/测试/预发/生产）
- 依赖的中间件清单
- 容量预估（机器数/QPS 承载/存储预估）—— **必须有数据依据**（呼应 `anti-ai-signs.md` 第 4 条）

### 7. 里程碑规划

新项目特有的章节。分阶段交付：

| 里程碑 | 交付内容 | 预估时间 | 依赖 |
|---|---|---|---|
| M1: 基础设施 | 数据库/框架/CI | 1 周 | 无 |
| M2: 核心功能 | <核心模块> | 2 周 | M1 |
| M3: 完整功能 | <全部模块> | 2 周 | M2 |
| M4: 上线 | 压测/灰度/全量 | 1 周 | M3 |

每个里程碑说清"交付什么"（可验证的产出物）。

### 8. 风险评估

新项目特有的风险维度：

| 风险类型 | 描述 | 缓解措施 |
|---|---|---|
| 技术风险 | 选型未验证/团队能力差距 | ... |
| 依赖风险 | 第三方依赖不稳定/有合规问题 | ... |
| 容量风险 | 预估数据量偏差/突发流量 | ... |
| 进度风险 | 里程碑延期 | ... |

### 9. 工时评估

按里程碑拆分，引用 `_backend-domain.md` 工时表：

| 里程碑 | 模块 | 工时(h) |
|---|---|---|
| M1 | 基础设施搭建 | xx |
| M2 | 核心功能开发 | xx |
| M3 | 完整功能开发 | xx |
| M4 | 测试 + 上线 | xx |
| | **合计** | **xxx** |

### 10. 实现速查

```markdown
### 10. 实现速查
- 整体架构图：见 2.1
- 技术选型：见 2.2
- 工程结构规范：见 3
- 核心数据模型：见 4
- 核心接口契约：见 5
- 部署架构：见 6

```

## 关键约束

1. **"技术选型"每项必须有选项对比 + trade-off** —— 这是对应 `anti-ai-signs.md` 第 2 条的强化。新项目的选型决策影响深远，无 trade-off 的选型是重大隐患。

2. **容量预估必须有数据依据** —— 呼应 `anti-ai-signs.md` 第 4 条。新项目的机器数、存储预估、QPS 承载，都要有依据（业务方给的预期、类似项目的数据），不能拍脑袋。

3. **无"改动点"和"数据库变更（迁移/回滚）"章节** —— 新建项目没有这些。如果发现自己写了"改动现有 XX"，说明这不是新项目，该用 generic-medium 配方。

4. **里程碑规划必须可验证** —— 每个里程碑的"交付内容"要是能验证的产出物（可运行的代码/可演示的功能），不是"完成 80% 开发"这种模糊描述。
