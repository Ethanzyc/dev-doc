# 配方：多任务场景（multi-task）

> **适用场景**：多个小优化合在一个需求里。
> 每个子任务可能单独看是"轻"方案，但合在一个需求里要统一规划。
> 后端领域决策点引用 `_backend-domain.md`。
> **目录**：核心差异 · 文档结构（1 背景 / 2 子任务清单 / 3 逐个子任务 / 4 整体 DDL / 5 整体上线 / 6 整体风险 / 7 整体工时 / 8 实现速查）· 关键约束

---

## 核心差异（和 generic-medium 的区别）

**章节按子任务重组，不是按技术维度平铺。**

每个子任务是一个"mini 方案"，有独立的改动/测试要点。但子任务之间的影响、依赖、上线顺序要在文档里统一规划。

---

## 文档结构

### 1. 需求背景

**写什么**：整体说明——为什么把这些小优化合在一起（同一个业务目标？同一批技术债？同一个上线窗口？）。

**不该写什么**：不要为每个子任务单独写一遍背景，那是冗余。

### 2. 子任务清单

用表格总览所有子任务：

| 子任务 | 影响范围 | 预估工时 | 优先级 | 依赖 |
|---|---|---|---|---|
| A: 优化券码生成性能 | VoucherService | 2h | 高 | 无 |
| B: 修复过期券清理 Bug | ExpireJob | 1.5h | 中 | 无 |
| C: 接口返回字段补全 | VoucherController | 1h | 低 | A |

**优先级**：高/中/低，决定上线顺序。
**依赖**：子任务之间是否有依赖关系（B 依赖 A 先上线？）。

### 3. 逐个子任务

每个子任务是一个独立小节，结构（按需裁剪，不要硬凑）：

```markdown
### 3.N 子任务 X：<名称>

#### 改动描述
（这个子任务改什么、为什么）

#### 数据模型 / 接口契约（如有）
（引用 `_backend-domain.md` 规范，无则跳过）

#### 改动点
| 类型 | 内容 |
| 改造 | ... |
| 新增 | ... |

#### 测试要点
（具体的测试场景，不写"编写单元测试"）
```

**子任务内部章节按需**：纯改 Bug 可能只有"改动描述 + 改动点 + 测试要点"，没有数据模型/接口契约。**不要为了凑结构硬写**。

### 4. 整体数据库变更

**汇总所有子任务的 DDL 变更**，统一编号：

| 子任务 | DDL 变更 | 回滚方式 |
|---|---|---|
| A | ALTER TABLE t_voucher ADD INDEX idx_code ... | DROP INDEX |
| C | 无 | - |

**关键**：多个子任务的 DDL 如果在同一上线窗口执行，要确认执行顺序和兼容性。

### 5. 整体上线方案

- **是否一次性上线**：所有子任务一起上，还是分批？
- **依赖关系**：B 依赖 A，那 A 必须先上或同时上
- **回滚策略**：一个子任务失败，是整体回滚还是只回滚该子任务？
- **回滚的可行性**：DDL 变更能否独立回滚（不能因为子任务 A 回滚把 B 也带走）

### 6. 整体风险评估

**重点评估子任务之间的相互影响**（这是 multi-task 配方特有的风险）：

| 风险类型 | 描述 | 缓解措施 |
|---|---|---|
| 子任务间影响 | A 改了 VoucherService 的方法签名，B 也调用该方法 | A 先上或同时上，B 做适配 |
| 上线顺序风险 | C 依赖 A，但 A 延期 | C 的上线窗口可独立调整 |
| 回滚耦合 | A 和 B 共改一张表，回滚 A 影响 B | DDL 变更设计为可独立回退 |

### 7. 整体工时评估

引用 `_backend-domain.md` 工时表，按子任务汇总：

| 子任务 | 功能 | 明细 | 工时(h) |
|---|---|---|---|
| A | 优化券码生成 | 改造 VoucherService.generate | 2 |
| B | 修复过期清理 Bug | 改造 ExpireJob.run | 1.5 |
| C | 接口字段补全 | 改造 VoucherController.query | 1 |
| | 测试 | 单元 + 集成 | 2 |
| | 联调 | 和前端 | 2 |
| | | **合计** | **8.5** |

### 8. 实现速查

索引各子任务的硬契约位置：

```markdown
### 8. 实现速查
- 子任务 A 改动：见 3.1
- 子任务 B 改动：见 3.2
- 子任务 C 改动：见 3.3
- 整体 DDL 变更：见 4
- 整体工时：见 7
```

---

## 关键约束

1. **子任务之间如果有依赖/冲突，必须在"整体风险评估"里点明**——这是 multi-task 配方最容易漏的地方。

2. **每个子任务都要能独立回滚**——不能因为一个子任务失败导致整体回滚。如果某个子任务的 DDL 变更不可独立回退，必须在风险评估里标红。

3. **子任务内部章节按需**——不要为了结构统一硬凑章节。纯改 Bug 的子任务写一堆"数据模型/接口契约"就是过度设计（呼应 `anti-ai-signs.md` 第 6 条）。

4. **优先级和依赖要明确**——这决定上线顺序，含糊会导致上线时混乱。
