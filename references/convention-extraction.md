# 规范域发现指引

> Phase 1 阶段 B 深度分析代码时加载本文件。
> 教 Agent 怎么从代码库扫描中**动态发现**团队工程约定，不预设固定清单。

---

## 规范源模式（先读：决定写入位置）

本文件所有"写入 `dev-doc/conventions/`"的描述，都按 SKILL.md Phase 1.3.0 的规范源模式区分：

| 模式 | 触发 | 写入位置 | 说明 |
|---|---|---|---|
| 从零模式 | 项目无现成约定源 | `dev-doc/conventions/<domain>.md` | skill 从零发现、累积 |
| 复用模式 | 项目已有 `.claude/rules/` 等 | `dev-doc/conventions/<domain>.md`（**仅增量**）| 规范源本身直接采信、不动；只把"源里没收的新约定"作为增量补到这里，文件头标注"为 `<规范源>` 的增量补充" |

**复用模式下**：规范源文件（如 `.claude/rules/sql.md`）是已确认的团队约定，**不要重新发现、不要让用户再确认一遍**。本文件的发现流程只用于抓增量。

---

## 核心流程

```
先探测项目规范源（见 SKILL.md 1.3.0）
  ↓        ├─ 复用模式：规范源 = .claude/rules/ 等，直接采信
  ↓        └─ 从零模式：规范源 = dev-doc/conventions/
阶段 B 深度分析代码
  ↓
对每个被读的代码区域，提取"这里体现了什么工程约定"
  ↓        （复用模式：只抓规范源没覆盖的增量）
聚类成规范域（相似归一类，不重叠）
  ↓
写入 dev-doc/conventions/<domain>.md（带时间戳 + 来源文件 + 置信度；复用模式标注增量）
  ↓
集中展示给用户确认/修正（复用模式只确认增量）
```

## 规范域文件的精确模板

每个发现的规范域写一个文件到 `dev-doc/conventions/<domain>.md`（复用模式的增量也写这里，见上方"规范源模式"）：

```markdown
# 规范域：<domain 名称，如 SQL / 数据模型>

## 提取时间
YYYY-MM-DD

## 来源文件
- src/main/resources/mapper/VoucherMapper.xml
- src/main/java/.../VoucherEntity.java
- （列出从哪些文件推断出来的）

## 推断的约定
- <约定 1：具体描述>
- <约定 2：具体描述>
- （每条约定要足够具体，能指导 DDL/API 设计）

## 置信度
<可信 / 待确认>

## 用户确认
[ ] 已确认
[ ] 已修正：（用户在此填修正内容）
```

---

## 置信度规则（两档）

| 置信度 | 条件 | 处理 |
|---|---|---|
| **可信** | 多个文件一致体现同一约定 | 直接采信，用户快速过一遍 |
| **待确认** | 单文件 / 少量推测 / 文件间有矛盾 | **重点请用户确认**，可能需要修正 |

置信度的意义：让用户在确认时知道精力该花在哪。"待确认"的条目才是真正的风险点。

## 常见规范域提示

**这只是提示，实际规范域由扫描结果决定。**不要硬套这个清单，也不要漏抓清单外的约定。

| 提示域 | 可能包含的约定 |
|---|---|
| 命名规范 | 类/方法/变量/常量的命名风格 |
| 分层架构 | 包结构、分层方式（controller/service/dao 还是 feature-based）|
| 接口规范 | 路径风格、版本化、返回结构、错误码体系 |
| SQL / 数据模型 | 表名前缀、主键规范、字段类型约定、索引命名 |
| 日志规范 | 日志框架、日志级别使用、关键日志格式 |
| 异常处理 | 异常体系、错误码定义、全局处理方式 |
| 配置管理 | 配置文件格式、环境区分、敏感信息处理 |

扫描时如果发现某个提示域在当前项目体现强烈，就建对应的规范域文件；如果发现清单外的约定（比如特殊的缓存使用规范），也要建文件。

## 示范样例：SQL 规范域

下面是一个**完整的规范域文件示例**，告诉 Agent "提取出来的规范该详尽到什么程度"。这个示例改编自一个 Java 后端项目的 Druid 解析器校验规则：

```markdown
# 规范域：SQL / 数据模型

## 提取时间
2026-06-19

## 来源文件
- src/main/resources/mapper/VoucherMapper.xml
- src/main/java/com/example/voucher/entity/Voucher.java
- src/main/resources/db/migration/V20231015__init_voucher.sql
- README.md（DDL 规范章节）

## 推断的约定
- 表名前缀：t_（所有业务表都以 t_ 开头）
- 主键：`id` 字段，类型必须为 `bigint(20) UNSIGNED NOT NULL AUTO_INCREMENT`
- `PRIMARY KEY (id)` 必须独立声明，不能内联在字段定义中
- int 类型必须带长度：`int(11)` 而非裸 `int`
- 索引名称长度不超过 30 字符
- 时间字段统一用 `datetime`，不用 `timestamp`（避免时区问题）
- 金额字段统一用 `decimal(18,4)`，不用 float/double
- 状态字段用 `tinyint`，对应 Java 枚举
- 软删除：`is_deleted tinyint(1) default 0`
- 所有表必须有 `create_time` 和 `update_time` 字段

## 置信度
可信（VoucherMapper + Voucher.java + migration SQL + README 四处一致）

## 用户确认
[ ] 已确认
[ ] 已修正：
```

**这个示例的几个要点**：
- 约定要**具体到能指导 DDL 设计**（"int(11) 而非裸 int" 比 "int 带长度" 好）
- 来源文件要**列全**，支撑置信度判断
- 每条约定是**观察到的模式**，不是"应该怎样"（这是用户确认环节的工作）

---

## 关键纪律

1. **提取的是"现状推测"，不是真规范** —— 代码库里的现有模式可能是坏习惯，不是团队想要的规范。所以**必须用户确认**，不能直接采信。

2. **不越界提取** —— 只提取阶段 A 圈定范围内代码体现的约定。不要因为"顺手翻到个相关文件"就扩大规范域范围。

3. **规范域之间不重叠** —— 聚类时要合并相似的。如果"SQL 规范"和"数据模型规范"内容高度重合，合并成一个。

4. **置信度要诚实** —— 不要为了好看把单文件推测标成"可信"。诚实标注才能让用户聚焦真正的风险。

5. **约定要具体** —— "命名要规范"不是约定，"表名以 t_ 开头"才是。模糊的约定无法指导后续设计。

6. **用户修正后要更新缓存** —— 如果用户确认时改了某条约定，立即更新 `dev-doc/conventions/<domain>.md` 的内容，后续章节加载的就是修正后的版本。

7. **domain 名 = 文件名 slug，定下不改** —— 规范域文件名（如 `sql.md`、`interface.md`）就是该域的 slug，`plan.md` 的"章节规划 + 规范域关联"表用**同一个 slug** 引用。命名规则：小写英文 + 短横线（`sql` / `interface` / `error-code` / `project-structure`）。一旦命名定下，不要中途改名——否则 Phase 4 按域加载会对不上文件、静默失败。
